## 개요

### Langfuse

이 글을 리뷰하기에 앞서, 왜 이 블로그가 추천되었는지부터 짚어 보려 한다.
Langfuse는 LLM 관측·평가 플랫폼이고, 우리와 비슷한 성격의 대시보드를 만드는 곳이다.
데이터를 모아 한 화면에 요약해 보여 주고, 거기서 자연스럽게 디테일로 들어갈 수 있게 한다.
다른 점이라면 그쪽은 LLM 사용 데이터이고, 우리는 센서나 카메라 등에서 가져온 데이터라는 점이다.

### ClickHouse

또한 Langfuse를 인수한 곳은 ClickHouse다.
ClickHouse는 대규모 데이터를 분석하기 위한 데이터베이스다.
Langfuse는 PostgreSQL에서 ClickHouse로 이전한 뒤 쿼리가 분단위에서 near-real-time 수준으로 빨라졌다고 한다.

우리처럼 데이터 분석 용으로 맞아 보여서, 도입을 고민 중이다.

## 무엇을 이야기하고 있는가?

해당 글의 주제는 Customizable Dashboard를 어떻게 설계하고 구현했는지다.

### Query Layer

핵심은 Frontend와 Backend 사이에 Query Layer를 하나 더 둔 것이다.
Frontend가 원하는 데이터 구조는 천차만별(customizable)이다.
어떤 데이터를 기준으로 필터를 하거나 정렬해서 보고자 할 것이고,
해당 글에서는 그것들을 어떻게 표현했는지에 대해서 언급했다.
Backend도 개발이 활발하다 보니 DB 구조가 자주 바뀐다.
Query Layer는 그 사이 변화를 중제하는 역할을 한다.

### Query Build와 Dashboard Build

글에서는 이 Query Layer를 Frontend와 Backend가 각각 어떻게 접근하는지 까지 다룬다.
Backend는 Query Build, Frontend는 Dashboard Build로 접근한다.

## 우리가 무엇을 얻을 수 있을까?

분야별로 나눠 보면 다음과 같다.

### Agent

Agent 쪽에서는 Langfuse 서비스 자체를 도입해 볼 수 있겠다.
백엔드는 이미 서비스 안정을 위해 여러 도구를 쓰고 있다.
API 요청을 보는 Sentry가 있고, GCP나 AWS 등의 클라우드 서비스에서는 SQL query 모니터링도 제공한다.
Agent도 이런 모니터링으로 LLM 정확도를 올리고, 고도화 지표로 삼을 수 있지 않을까 싶다.

### Frontend

Frontend에서는 Dashboard Builder를 살펴보는 편이 도움이 될 것 같다.
이 글처럼 대시보드 구성을 사용자에게 자유롭게 열어 주자는 얘기 보다는,
위젯 하나를 만들 때부터 재사용 가능하게 짜기 위해서 도움을 줄 것으로 기대한다.

### Semantic Layer

전체적으로는 이런 semantic layer를 공용으로 두면 여러 면에서 이득이 있다.
프론트엔드, 백엔드뿐 아니라 Agent까지 같은 스키마를 보게 된다.
백엔드에서 데이터를 처리할 때에 Agent용과 프론트용을 나누지 않고 하나로 모을 수 있지 않을까 기대한다.
결국 프론트에서 보는 데이터가 agent에도 똑같이 제공되어야 온전한 결과를 줄 수 있을 것이라 생각했다.
